# GitHub Wiki & API Documentation

How the Pantry App documentation is split between GitHub Wiki and GitHub
Pages, and how doc comments feed them.

## Architecture

```
GitHub Wiki (hand-maintained)          GitHub Pages (auto-generated)
  Home.md                                index.html      (landing page)
  _Sidebar.md                            api/            (dart doc output)
  _Footer.md                             .nojekyll
```

- **Wiki** at `github.com/Thigas-Tech/pantry_app/wiki` -- manual content
  (Home, sidebar, footer). Does NOT receive auto-generated docs.
- **GitHub Pages** at `thigas-tech.github.io/pantry_app/` -- API
  documentation generated by `dart doc`. The `api/` subdirectory holds
  the full HTML output. When Flutter Web is built, its files will replace
  `index.html` at the root, and the API docs remain at `api/`.

## How doc comments become API docs

1. `dart doc .` reads every `///` doc comment in the source tree.
2. It generates static HTML files in `doc/api/`.
3. The CI workflow (`.github/workflows/wiki.yml`) copies those files
   into the `api/` directory of the `gh-pages` branch.
4. GitHub Pages serves them at `thigas-tech.github.io/pantry_app/api/`.

**Garbage in, garbage out.** Write doc comments as proper sentences --
they are the user-facing API documentation.

## Doc comment conventions (brackets, not backticks)

[dart doc] treats `[square brackets]` as **cross-references**. It resolves
the name inside brackets to a known symbol (class, method, typedef, etc.)
and emits a clickable link in the generated HTML.

Backticks `` ` `` in doc comments are rendered as **inline code** -- plain
monospace text with no link. This is how Markdown works, and [dart doc]
follows the same pattern.

| What you write | What dart doc generates |
|---|---|
| `Uses [DatabaseHelper] to read data.` | Clickable link to the DatabaseHelper page |
| `Uses `DatabaseHelper` to read data.` | Plain monospace text, no link |
| `See [MyClass.myMethod].` | Clickable link to myMethod on MyClass |
| `Pass a [http.Client] for testing.` | Clickable link to the http.Client class |

**Rule**: when referencing public API, use brackets `[]`. Only use backticks
for literal code values (`true`, `null`, `"string"`, `42`).

When the `comment_references` lint fires, add the missing import -- never
switch to backticks to silence it.

## Wiki structure (hand-maintained only)

```
wiki/
  Home.md                  Landing page with links
  _Sidebar.md              Navigation sidebar
  _Footer.md               Footer text
```

These three files are manually maintained. The wiki does NOT contain
auto-generated content.

## Manual wiki update

```bash
git clone git@github.com:Thigas-Tech/pantry_app.wiki.git /tmp/wiki
# Edit Home.md, _Sidebar.md, or _Footer.md
cd /tmp/wiki
git add -A && git commit -m "Update wiki content" && git push
```

## CI/CD automation

See `.github/workflows/wiki.yml` for the full workflow.

The workflow:
1. Triggers on push to `main` (and manual `workflow_dispatch`).
2. Checks out the source repository.
3. Runs `flutter pub get` and `dart doc .`.
4. Checks out the `gh-pages` branch.
5. Replaces `api/` with fresh docs from `doc/api/`.
6. Commits and pushes to `gh-pages`.

## GitHub Pages setup (one-time)

The GitHub Pages source was switched from `main` `/` to `gh-pages` `/`
so the landing page and API docs are served. The `.nojekyll` file
disables Jekyll processing (required for `dart doc` HTML files).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Pages shows old docs | CI didn't run or failed | Manually trigger via Actions tab |
| `dart doc` has warnings | Missing imports for bracket references | Add the import, re-run `dart doc .` |
| Broken links in API docs | Bracket reference targets a private symbol | Only use brackets for public API |
| Pages not updating | gh-pages branch not checked out by CI | Ensure `origin gh-pages` exists and is branch default for Pages |
| `comment_references` lint fires | Missing import | Add the import -- never suppress the lint |
